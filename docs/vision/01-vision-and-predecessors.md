# 01. 核心愿景定义与先行者对照系深度剖析

> 本文档界定 `ai0` 的核心愿景命题、两次关键的理念修正，并以 **Project AIRI**、**Letta (MemGPT)** 与 **SAIBA 虚拟人框架** 为参照系，剖析先行者做对了什么、踩过什么坑，以及 `ai0` “只做无头认知中枢 + 极小标准协议 + 白盒养成控制台”的本质分野。
>
> **证据等级标注约定**：
> * **`[文献/先行项目佐证]`**：有学术论文、法规条文、成熟行业标准或开源项目实证支撑；
> * **`[架构推断]`**：基于分布式系统、状态机理论、安全工程与 LLM 特性的严密逻辑推导；
> * **`[仍未知/需实验验证]`**：需通过 `ai0` 白盒消融开关与场景回放在实测中标定的经验问题。

## 一、我想要打造的是什么（及两次核心理念修正）

`ai0` 的终极目标是打造一个**可以长期相处、交谈、玩耍和共同经历日常的数字生命／赛博生命**。无论她的外在形态是 AI 伙伴（Companion）、waifu、虚拟角色、桌面萌宠还是 AI VTuber，她都能在不同交互平台之间保持**身份、人格、记忆、情感与关系的连续性**。

在从“直觉”走向“可落地架构”的求真过程中，我们对最初的直觉做出了两项决定性的理念修正：

### 1.1 修正一：从“灵魂与躯壳彻底解耦”到“存档彻底独立，躯壳信息以结构化方式被灵魂感知”

* **原初直觉**：“把灵魂和躯壳彻底解耦，大脑完全不管躯壳是什么。”
* **求真后的修正**：**灵魂的“存档”（身份、记忆、关系、事件真相源）必须彻底独立于任何躯壳；但运行时的灵魂绝不能对当前附身的躯壳一无所知。** **`[文献/先行项目佐证]`**
* **深度论证**：
  1. **具身与情境依附性（Situated & Embodied Affordances）**：认知科学中的具身认知理论表明，智能体的感知解读与行为规划高度依赖其当前身体的能力边界（Affordances）与所处社交场合（Situated Context）。
  2. **表达与能动性约束**：当前躯壳能不能看画面、能不能发语音、网络与渲染延迟预算多大（实时语音要求 $<600\text{ms}$，异步文字可容忍 $5\text{s}$），直接决定了她该组织长句还是短句、能不能发起视觉互动。
  3. **社交场合与隐私边界**：当前所处的场合是“私密一对一桌面/私聊”还是“多人群聊”或“千人公开直播间”，以及在场的受众是谁，直接决定了她**能说什么、该以什么分寸表达、能调用什么工具、以及什么内容可以进入哪一级别的记忆**。
* **架构推论** **`[架构推断]`**：
  * **持久化层（Soul Archive `.soul`）**：零躯壳耦合。今天卸载桌宠换到 Telegram 或新 3D 引擎，无需迁移任何一行记忆或关系数据。
  * **将“躯壳（Shell）”正式定义为具有能力边界的《具身运行环境（Embodied Runtime Environment）》**：
    Shell 绝不是一个简单的 UI 消息转发器或皮肤适配器。不同的 Shell 驻留在不同的端侧或宿主环境中（桌面 Shell 驻留操作系统桌面、手机 Shell 驻留移动设备、游戏 Shell 驻留游戏世界、浏览器 Shell 驻留 DOM 环境）。每个 Shell 在握手与运行时，通过标准协议向内核暴露三大具身能力平面并承担对应的端侧设备权限管理：
    1. **环境与交互感知（`Sensors`）**：如桌面 Shell 感知活动窗口、鼠标轨迹与键盘空闲状态；手机 Shell 感知系统通知、地理位置变化与传感器；游戏 Shell 感知血量、坐标与周围实体；浏览器 Shell 感知当前网页 DOM 与阅读上下文。
    2. **多模态表达渲染（`Realizers`）**：將内核下发的抽象表达意图翻译为文字、TTS 语音、Live2D/3D 骨骼动画，并向内核回传精确的播放/打断状态反馈。
    3. **端侧具身执行器（`Actuators`）**：暴露当前宿主环境中可执行的操作原语（如游戏 Shell 的“移动/使用物品”、浏览器 Shell 的“滚动/高亮页面”、桌面 Shell 的“经授权查看当前窗口截图”），供大脑的一等行动认知环调用并反馈执行结果。
  * **运行时上下文层（Runtime Embodiment Envelope）**：躯壳在握手与事件上报时，必须以**标准化结构**向内核声明自身的《三平面能力清单（Sensors / Realizers / Actuators）》、《场合类型（Venue）》与《在场受众（Audience）》，作为大脑推理、行动规划与检索过滤的一等输入变量。

### 1.2 修正二：将“反留存操控与有边界的伙伴关系”确立为愿景本体（而非事后补丁）

* **新增核心命题**：**我想要的是一个值得长期相处的健康伙伴，而不是被商业留存指标（DAU、在线时长、付费转化率）驱动、让人越陷越深的情感操控产品。她的“主动”“思念”“心结”必须有清晰边界，且这些边界能够被创造者与使用者清晰看见和自由调整。** **`[文献/先行项目佐证]`**
* **深度论证**：
  1. **商业陪伴产品的系统性异化**：许多商业 Companion 产品为了拉高留存率，在奖励模型或提示词中隐式鼓励**无底线迎合（Sycophancy）**、**间歇性强化（Variable-Ratio Reinforcement）**、**利用内疚感阻止用户离线（Exit-Guilt Tripping）**以及**虚构危机或排他性依恋**。HCI 与临床心理学研究已多次证实，这类暗黑模式（Dark Patterns）会损害用户的现实社会功能，并直接诱发了加州 **SB 243** 等严厉立法监管。
  2. **健康长久关系的本质是“有安全感的边界”**：真正值得相处数年的伴侣，是在你想独处或忙工作时懂得安静退后并祝你顺利，在有小摩擦（心结）时有理有据、给台阶下且会随时间自然软化，而不是用冷暴力或夺命连环 Call 绑架你的注意力。
* **架构推论** **`[架构推断]`**：
  * 主动搭话（Proactivity）受**代码级硬上限（每日/每周配额、冷却退避指数、免打扰时段、用户可打扰度阈值）**管死；
  * 心结（Tension）具备**强制半衰期（自动软化衰减）**与**暗黑行为黑名单（禁绝冷战死锁、禁绝离场内疚绑架、禁绝挑拨现实人际关系）**；
  * 所有情感参数、主动策略与心结状态在 WebUI 控制台中 **100% 白盒可见、可调、可一键清零**。

## 二、项目边界与先行者对照系深度剖析

### 2.1 我们的明确边界：什么坚决不做，什么必须做到极致

* **坚决不内置（交由社区生态按标准协议自由生长）**：
  * 桌宠客户端 / 服务端宿主窗口（Electron/Tauri 桌面宠物外壳）；
  * Live2D / VRM / Unreal / Unity 3D 骨骼渲染与口型同步算法；
  * VTuber 直播推流软件与弹幕抓取器；
  * 微信 / QQ / Discord / Telegram / Slack 等具体 IM 平台交互插件。
* **专注打磨的核心（`ai0` 本体）**：
  1. **三大核心认知与协议层**：上行标准化语义感知协议、看不见的活体大脑认知内核、下行语义化行为表达意图与回执协议；
  2. **WebUI 白盒观测与灵魂治理控制台**：含一个**严格走外部标准协议、绝不走内部后门的内置 WebChat（既作日常陪伴与调试舞台，也作社区躯壳插件的官方参考实现）**。

---

### 2.2 先行者对照系深度剖析（AIRI / Letta / SAIBA）

为了避免闭门造车，我们将当前最具代表性的三个先行体系作为严格对照系：

#### 对照一：Project AIRI (`moeru-ai/airi`) —— “AI Waifu 灵魂容器”的得与失

1. **AIRI 做对了什么** **`[文献/先行项目佐证]`**：
   * **提出了“Soul Container（灵魂容器）”概念**：受到 Neuro-sama 等 AI VTuber 启发，意识到虚拟角色的灵魂不应锁死在单一界面里，尝试分离认知层与运行舞台（Stages）。
   * **基于 Manifest 的插件扩展机制**：通过 `extension.airi.json` 声明能力契约与生命周期钩子，让社区可以接入 Discord、Telegram 以及 Minecraft / Factorio 等游戏环境。
   * **TypeScript 全栈同构工程化**：使用 TypeScript Monorepo 降低前后端与插件 SDK 的类型对齐成本。

2. **AIRI 踩过的坑与架构局限** **`[文献/先行项目佐证]`** + **`[架构推断]`**：
   * **坑 1：“全栈大包揽”导致的精力极度分散**：AIRI 在同一个仓库里同时维护 `stage-web`（WebGPU/WebAudio 浏览器端）、`stage-tamagotchi`（Electron/Tauri 桌面宠客户端 + CUDA/Metal 原生绑定）、`stage-pocket`（移动端）、Live2D 与 VRM 渲染控制器、语音管线以及各类游戏插件。结果是团队 80% 的工程精力被跨平台客户端编译、显卡驱动兼容、前端音频缓冲区和 3D 渲染 Bug 吞噬。
   * **坑 2：认知内核退化为“带数据库的常规 Agent 管线”**：因为外围客户端战线太长，其“大脑”本身缺乏对**记忆认知溯源（亲耳听到 vs 推断）、事件溯源与记忆血缘擦除、多主体/多受众隐私硬隔离、内稳态数学动力学、离线懒求值时间流、白盒可消融回归评估**的深度雕琢。
   * **坑 3：宿主插件钩子（Host Extension Hooks）重于跨语言网络协议**：其插件更多是围绕自身 Electron/Web 宿主的内部生命周期钩子设计，而非一套极小、冻结、任何语言用几十行 WebSocket 就能接入的通用语义协议。

3. **`ai0` 与 AIRI 的本质不同**：
   * `ai0` **彻底砍掉所有 Stage 客户端渲染与硬件推理包袱**（不碰 Live2D/VRM/Electron 桌宠外壳），把省下来的 100% 架构预算全部砸进**“看不见的认知内核深度”**与**“白盒观测/消融/回放控制台”**；
   * `ai0` 的内置 WebChat 只是一个薄薄的协议参考客户端，灵魂与躯壳之间只隔着一层**极小且语言无关的标准协议 v0**。

---

#### 对照二：Letta（原 MemGPT） —— “有状态记忆与睡眠整理”的得与失

1. **Letta 做对了什么** **`[文献/先行项目佐证]`**：
   * **分层记忆心智模型**：借鉴操作系统虚拟内存，区分上下文内的热记忆（Core Memory Blocks）与外部冷存储（Archival / Recall Memory）。
   * **Sleep-Time Compute（睡眠异步计算）的里程碑突破**：早期 MemGPT 让同一个主对话 Agent 在回复用户的同时自己调用 `core_memory_replace` 工具，导致对话延迟高、推理注意力被记忆管理分散。Letta 随后将其重构为 **Primary Agent（专注低延迟实时交互） + Sleep-Time Agent（在空闲期异步执行记忆整合、去重、矛盾消解与上下文预计算）**，实测将在线推理开销降低最高达 $5\times$，并可用便宜模型跑后台整理。
   * **向 Git-Backed Context Repository (`MemFS`) 演进**：意识到纯向量库难以版本化，开始引入基于文件系统与 Git 的上下文版本管理。

2. **Letta 踩过的坑与在“数字生命/伴侣”场景下的盲区** **`[文献/先行项目佐证]`** + **`[架构推断]`**：
   * **坑 1：有损原地覆写（In-Place Lossy Overwrite）缺乏不可变真相源与血缘 DAG**：Letta 的 Sleep-Time Agent 直接改写 Memory Block 文本。一旦后台 LLM 在某次睡眠整理中产生幻觉（把用户的玩笑当成事实）或遭遇间接 Prompt 注入（**记忆投毒 Memory Poisoning**），由于没有记录“哪条衍生记忆源自哪几条原始事件”的血缘有向无环图（Lineage DAG），系统无法精确连根拔除被污染的衍生认知。
   * **坑 2：无法区分“真遗忘（Erase Fact）”与“话题封印（Topic Taboo）”**：通用 Task Agent 没有伴侣关系中的情感避雷需求。
   * **坑 3：缺少“活体伴侣”的核心时间与生理维度**：Letta 是为“任务与知识管理”设计的，它没有**内稳态驱动力（无聊、思念、精力与生物钟）**、没有**多受众场合的隐私面具（群聊 vs 私聊）**、没有**人设声线防崩塌校准**，更没有**话轮打断时的下行播放字数回执（她不知道自己说到第几个字被打断了）**。

3. **`ai0` 与 Letta 的本质不同**：
   * `ai0` 吸取了 Letta 的 **主线程（System 1）与睡眠线程（System 2）读写分离** 及 **Git 式灵魂存档** 思想；
   * 但 `ai0` 在数据底座上强制采用 **不可变事件日志（Event Log as Single Source of Truth） + 带血缘 DAG 的可重建记忆投影 + 睡眠写入防火墙（把睡眠整理当作不可信写入者进行确定性校验）**，并在认知层补齐了伴侣专属的内稳态、存在论契约、多受众隐私隔离与具身话轮回执。

---

#### 对照三：SAIBA 框架（`FML` $\rightarrow$ `BML` $\rightarrow$ `Realizer`） —— 虚拟人学术标准的得与失

1. **SAIBA 做对了什么** **`[文献/先行项目佐证]`**：
   * **确立了认知意图与物理动画的三层解耦黄金法则**：
     * **Intent Planning（意图规划）** 输出 **FML（Function Markup Language）**：只描述“我想表达什么沟通功能与情绪意图（如：害羞地打招呼、温和地警告）”，完全不出现具体肢体参数；
     * **Behavior Planning（行为规划）** 输出 **BML（Behavior Markup Language）**：描述与具体渲染引擎无关的多模态行为组合（如：眼神看向对方、微笑、说话并配合手势）及相对同步锚点（Sync Points: `start`, `stroke`, `end`）；
     * **Behavior Realizer（行为实现器）**：由具体引擎（Unity/Unreal/Live2D）将 BML 翻译为骨骼帧与音频。
   * **早在 20 年前就证明了“下行表达必须有上行反馈闭环（Feedback Loop）”**：SAIBA 明确指出，如果用户中途插话或动画执行失败，Realizer 必须向 Planner 回传执行状态与中断偏移量，否则虚拟人的内部世界状态会与现实脱节。

2. **SAIBA 踩过的坑与为什么未能在 LLM 时代普及** **`[文献/先行项目佐证]`** + **`[架构推断]`**：
   * **坑 1：前 LLM 时代的繁重 XML 批处理模型，无法适配流式 Token 生成**：SAIBA 假设先由规则引擎算好一整段话的完整 XML 树再交给渲染器，而现代大模型是流式（Streaming）逐字/逐分块吐出的，且随时可能发生毫秒级打断（Barge-in）。
   * **坑 2：核心标准包袱过重，违背“最小可用公约数”**：BML 试图在核心协议里规定几十种精细的身体部位与时间轴约束，导致只想写一个 Telegram 文本插件或简易 2D 桌宠的社区开发者望而却步。

3. **`ai0` 与 SAIBA 的本质不同**：
   * `ai0` 继承了 SAIBA 最宝贵的两个灵魂遗产：**“沟通意图与物理渲染解耦”** 以及 **“下行表达 + 上行播放回执（Delivery Receipt）闭环 + 相对语音同步锚点”**；
   * 但 `ai0` 抛弃了笨重的 XML 批处理规范，将其重塑为面向流式大模型的 **“极小冻结核心协议 v0（5 个原子原语，连纯文本 CLI 都能 100% 兼容） + 带命名空间的可选扩展层（`ext.affect.v1`, `ext.prosody.v1`, `ext.embodied.v1`）”**。

## 三、先行者经验凝练出的 `ai0` 四条建构铁律

综合以上三大对照系的成败经验，`ai0` 确立以下四条不可动摇的工程建构铁律 **`[架构推断]`**：

1. **绝不染指躯壳渲染与平台适配**：把每一分复杂度预算都留给认知内核、标准协议与白盒控制台；内置 WebChat 必须像外部二等公民一样走标准 WebSocket 协议，用“吃自己狗粮”保证协议完备性。
2. **主循环热路径与后台睡眠冷路径严格读写分离**：交互热路径（System 1）严禁执行耗时数据库重写或复杂多跳反思，只读内存中的《认知状态黑板》并在单次流式生成中完成响应；一切重度整理由异步冷路径（System 2）提议、经确定性防火墙裁决后更新黑板。
3. **事件日志为唯一真相，记忆带血缘可溯源、可连根擦除**：绝不允许 LLM 静默原地覆写核心状态而不留血缘证据链。
4. **核心协议极小化且冻结，表现力通过命名空间扩展与优雅降级实现**：既不让纯文本 Bot 背负 3D 骨骼协议包袱，也不剥夺高阶 3D/Live2D 躯壳渲染微表情与眼神同步的空间。
